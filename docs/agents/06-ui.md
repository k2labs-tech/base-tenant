# UI — layouts, screens and components

**Module:** core · **Package version:** v2 · **Last reviewed:** 2026-08-18

## When to use this

You are building a screen in the host application and need to know which
layout to sit it in, which package component to drop into it, or which route
already serves the thing you were about to write.

## When NOT to use this

- Deciding what a *new* management screen looks like. That is one pattern for
  the whole codebase and it lives in [02-conventions.md](02-conventions.md).
- Styling. The package compiles nothing and publishes no assets; the host
  builds the CSS and points its `@source` at these views. See `docs/FRONTEND.md`.

## Layouts

Two, both under the `base-tenant::` view namespace:

| View | Used by | What it draws |
|---|---|---|
| `base-tenant::layouts.app` | every authenticated screen | Flux sidebar (menu + user menu), sticky header with breadcrumbs, account switcher, notification bell, impersonation banner, `flux:main` |
| `base-tenant::layouts.guest` | login, register, password, 2FA challenge, presale landing | centred card, logo, no chrome |

A package screen picks one with the Livewire attribute:

```php
use Livewire\Attributes\Layout;

#[Layout('base-tenant::layouts.app')]
class BookingManager extends Component {}
```

A Blade view picks one with the registered component:

```blade
<x-base-tenant::app-layout>
    {{-- page --}}
</x-base-tenant::app-layout>
```

### Pointing them at your own

```php
// config/base-tenant.php
'layouts' => [
    'app' => env('BASE_TENANT_LAYOUT_APP', 'base-tenant::layouts.app'),
    'guest' => env('BASE_TENANT_LAYOUT_GUEST', 'base-tenant::layouts.guest'),
],
```

**Trap:** nothing inside the package reads that key yet. Every package
component hardcodes `#[Layout('base-tenant::layouts.app')]`, so setting
`BASE_TENANT_LAYOUT_APP` alone changes nothing while you are running on the
package as a dependency. The key becomes real after
`php artisan k2labs-base:scaffold`, which copies the code into the application
and rewrites the namespace — from then on the config is the single place to
change the chrome. Until then, use the key in **your own** components:

```php
#[Layout(self::layout())]   // or, in render(): ->layout(config('base-tenant.layouts.app'))
```

### `@stack('scripts')`

Both layouts end with:

```blade
@livewireScripts
@fluxScripts
@stack('scripts')
```

A component that ships its own JavaScript pushes it there —
`base-tenant.files.uploader` is the one in the package that does, and it is
where the whole signed-upload dance lives. **A `@push('scripts')` with no
matching stack is discarded silently**: no error, no console warning, just a
drop zone that does not react to a dropped file. If you replace the layout,
carry the stack, and keep it *after* `@livewireScripts`.

The app layout also expects `@fluxAppearance` in the `<head>`. Without it the
page paints light and then flips to dark on the first frame.

## Embeddable components

The ones meant to be dropped into a host view. Parameters are exactly what
`mount()` accepts.

### Files

```blade
<livewire:base-tenant.files.uploader :fileable="$property" collection="photos" :multiple="true" />
<livewire:base-tenant.files.gallery :fileable="$property" collection="photos" :can-delete="true" />
<livewire:base-tenant.files.usage-badge />
```

`fileable` is optional — omit it for account-level files. `collection`
defaults to `library`, `multiple` and `canDelete` to `true`. The gallery
listens for `file-uploaded`, so a file appears the moment the uploader
finishes; the badge listens too. See [11-files.md](11-files.md).

### Onboarding

```blade
<livewire:base-tenant.onboarding.checklist />
```

No parameters. Renders nothing once the account has finished or dismissed it.
Already on the package dashboard. See [23-onboarding.md](23-onboarding.md).

### Pre-sale

```blade
<livewire:base-tenant.presale.pricing-table />
<livewire:base-tenant.presale.waitlist-form source="landing" />
```

The pricing table takes no parameters — it renders `config('base-tenant.plans')`,
which is the same config the feature gates read, so the page cannot promise
something the product does not enforce. `source` is a free-text tag stored with
the waiting-list entry. Both are on `base-tenant::presale.landing`. See
[26-presale.md](26-presale.md).

### Profile

```blade
<livewire:base-tenant.profile.connected-accounts />
```

No parameters. Lists the enabled social providers and which of them this user
has linked, and is the **only** place a provider may be attached to an existing
account. It refuses to unlink the last credential when the user has no
password. See [21-social-login.md](21-social-login.md).

### Account switcher

```blade
<livewire:base-tenant.account-switcher />
```

No parameters. Already in the app layout header (hidden below `sm`). What it
shows depends on who is looking:

- **A customer** sees their own accounts — one account with `multi_team` off,
  so the component renders the name as plain text rather than a dropdown of
  one item. With `BASE_TENANT_MULTI_TEAM=true` it is the list they belong to.
- **Platform staff** (`is_admin`, i.e. `$user->isSuperAdmin()`) see *every*
  account, plus an amber `staff` badge on the trigger so it is never ambiguous
  whose data is on screen. The list is capped at `SEARCH_THRESHOLD * 5` rows;
  above `SEARCH_THRESHOLD` (10) accounts a live search box appears in the
  dropdown and is the way through. The cap is what makes the search necessary
  rather than decorative — an installation with four thousand customers would
  otherwise build four thousand rows to draw a dropdown.

`switchAccount($id)` re-checks the permission server-side (`isSuperAdmin()`
or `belongsToAccount()`) because the id arrives from the browser and a list
that omits an account does not stop anyone naming it. It writes
`last_account_id`, refreshes the roles session, and redirects to the dashboard
with `navigate: false` — the whole role and menu context changed, and a SPA
swap would keep the old one.

Staff entering a customer account writes an `account.entered` entry into **that
account's** activity log. `leaveAccount()` steps back out to the platform view
(`Tenant::forget()`, `last_account_id` nulled) and is refused for anyone who is
not staff: everybody else is always inside an account, and leaving would put
them somewhere with nothing on it.

### Notification bell

```blade
<livewire:base-tenant.notification-bell />
```

No parameters. Already in the app layout header. Unread count plus the latest
`config('base-tenant.notifications.dropdown_limit')` (10) notifications,
flattened to arrays of `title`, `message`, `action_url`, `priority`, `icon`,
`read_at`, `time_ago`. It polls — `wire:poll.{interval}s` from
`config('base-tenant.notifications.polling_interval')`, 30 by default — and
also refreshes on the `notificationRead` event, which it both listens for and
dispatches so a second bell on the page stays in step. `markAsRead($id)` and
`markAllAsRead()` go through `NotificationService`. The full page is
`base-tenant.notifications.index`.

### Alerts table

`base-tenant.alerts.table` is **a placeholder**: its view is an empty `<div>`
and it displays nothing. Build the screen with the table pattern in
[02-conventions.md](02-conventions.md) instead.

## Blade components

Two are registered as class components in `registerBladeComponents()`:

```blade
<x-base-tenant::app-layout>   {{ $slot }} </x-base-tenant::app-layout>
<x-base-tenant::guest-layout> {{ $slot }} </x-base-tenant::guest-layout>
```

Three are anonymous views resolved through the `base-tenant::` namespace:

```blade
<x-base-tenant::social-buttons :label="__('auth.or_continue_with')" />
<x-base-tenant::social-icon provider="google" />
<x-base-tenant::application-logo class="h-16 w-16 fill-current" />
```

`social-buttons` renders nothing when no provider is enabled, and draws its own
grid and separator; `label` is optional and falls back to
`base-tenant::social.continue_with`. `social-icon` inlines the official mark in
brand colour — the package serves no assets, so the SVG is in the view.
`application-logo` is the placeholder every application is expected to replace.

**No anonymous component path is registered, on purpose.** The bare
`<x-social-buttons>` does not resolve: that name belongs to the host, and a
short alias would stop resolving the moment the code is scaffolded into the
application. Always write the `base-tenant::` prefix.

Everything else — fields, buttons, modals, tables — is a Flux primitive.
There are no `<x-base-tenant::input>`-style wrappers left after the redesign.

## Blade directives

```blade
@feature('api_access')
    <flux:button :href="route('api.tokens')">…</flux:button>
@endfeature

@withinlimit('checks.run')
    <flux:button wire:click="run">…</flux:button>
@else
    <flux:callout>{{ __('app::limits.reached') }}</flux:callout>
@endwithinlimit
```

`@feature` is `Feature::active()` — is this in the plan at all. `@withinlimit`
takes a **metric**, not a feature, and an optional increment
(`@withinlimit('checks.run', 5)`): what the screen needs to know is whether
there is room left, and only the meter can answer that. With the metering
module off there is no ceiling, so it is always true.

Both are `Blade::if`, so `@else`, `@elsefeature` and `@unlessfeature` work.
Hiding a button is not enforcement — the action behind it still has to check.

## Management screens

Every table screen in the package — `UserManager`, `AccountManager`,
`RoleManager`, `FileLibrary`, `ActivityLog`, `TransferManager` — is the same
pattern: `InteractsWithTable`, a `sortableColumns()` whitelist, and a fixed
page layout of breadcrumbs, header, optional context strip, then a panel
holding toolbar (search | filter | view), table and footer.

It is written out once, with the trait's contract and the `TablePatternTest`
that enforces it, in [02-conventions.md](02-conventions.md#management-screens).
Copy `UserManager`. Do not invent a second shape.

## Anti-patterns

```php
// ✗ Renders the screen with no chrome: no sidebar, no breadcrumbs, no
//   account switcher, and no `@stack('scripts')` for anything it embeds.
class BookingManager extends Component {}

// ✓
#[Layout('base-tenant::layouts.app')]
class BookingManager extends Component {}
```

```blade
{{-- ✗ Resolves to nothing. No anonymous component path is registered, and
     the bare name is the host application's to use. --}}
<x-social-buttons />

{{-- ✓ --}}
<x-base-tenant::social-buttons />
```

```php
// ✗ Throws a RouteNotFoundException on any installation with the module off,
//   from a page that has nothing to do with files.
route('base-tenant.files.index');

// ✓ Inside the same gate, or from the menu, which is already filtered.
Module::enabled(Module::FILES) ? route('base-tenant.files.index') : null;
```

```blade
{{-- ✗ The directive hides the button; the method still runs when someone
     posts to it. --}}
@withinlimit('checks.run')
    <flux:button wire:click="run">…</flux:button>
@endwithinlimit

{{-- ✓ Hide it *and* refuse it. --}}
public function run(): void
{
    Meter::incrementOrFail('checks.run');
}
```
